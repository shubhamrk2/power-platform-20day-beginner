Phase 1 · Days 1–4

Foundations

Before you build anything, get comfortable with the cloud and learn how data is stored and shaped. These four days are the ground everything else stands on. Every line of code, every flow, every chart you build in Days 5–20 connects back to what you set up here.

Day 1

Getting your bearings: the cloud, Microsoft 365, Power Platform

~90 minutes

Concept — what is "the cloud"?

Plain English: "the cloud" means powerful computers in a data centre somewhere that you use through your web browser. You don't install anything — you open a website, sign in, and the work happens on Microsoft's computers, not yours. That's why any device with a browser works.

A bit more technical: the tools are web applications. Your browser sends requests over the internet to Microsoft's servers. Those servers do the computation and send back the screen you see. Your creations (tables, apps, flows) are saved on those servers, so you can sign in from any device and find them again.

Concept — the words every beginner must know
  • Browser — the program for visiting websites. Microsoft Edge and Google Chrome are the two you'll use. Both came with your computer.
  • Tab — one website open inside the browser window, like a page in a book. You can have many tabs open at once.
  • URL / address — the web address you type at the top bar, e.g. make.powerapps.com. Press Enter after typing it.
  • Sign in — proving who you are with an email address + password. Different accounts (work, personal) are completely separate.
  • Incognito / private window — a browser window that forgets all sign-ins when you close it. Keeps your learning account clean.
Concept — Microsoft 365 and Power Platform: how they relate

You signed up for Microsoft 365 E5. This gives you the familiar Office apps (Word, Excel, Teams, SharePoint, Outlook) and the whole Power Platform. Both share one identity system called Microsoft Entra ID (formerly "Azure Active Directory") — so the same email + password that opens Outlook opens Power Apps. There is only one user account; everything flows from it.

  • Power Apps — build apps. Phase 2.
  • Power Automate — build automations ("flows"). Phase 3.
  • Copilot Studio — build AI chatbots. Phase 5.
  • Power BI — build charts and dashboards. Phase 6.
  • Dataverse — the shared database underneath it all. Day 2 onwards.
Concept — tenant, environment, and solution (the three "rooms")

Think of the Microsoft cloud like a building:

  • Tenant — the whole building. Your entire organisation's space in Microsoft's cloud. Every user, every app, every file lives inside it. The tenant has a domain like yourtenant.onmicrosoft.com.
  • Environment — a room inside the building. An isolated container with its own Dataverse database, its own security settings, and its own URL (like org12345.crm.dynamics.com). You can have many environments: one for learning, one for testing, one for production. What you build in the Learning environment cannot affect any other environment.
  • Solution — a labelled box inside a room. Groups your tables, apps, and flows so you can manage and move them together. You'll create this on Day 4.
Concept — the maker portal and every menu item explained

The maker portal at make.powerapps.com is your main workshop. Here is what every left-nav item does:

  • Home — quick-start templates and recent items.
  • Apps — list of all canvas and model-driven apps you've created.
  • Tables — all Dataverse tables in the current environment. Where you build your data model.
  • Flows — shortcut to Power Automate for this environment.
  • Chatbots — shortcut to Copilot Studio.
  • Solutions — the boxes that group everything together. You'll live here from Day 4.
  • Dataflows — tools to import and clean data from files/databases into Dataverse tables.
  • Connections — the authenticated links to external services (Outlook, SharePoint, etc.) that your flows and apps use.
  • Custom connectors — bridges to external web APIs that don't have a built-in connector.
  • AI models — pre-built AI models (invoice scanning, text classification, object detection) you can call from apps and flows.

The environment picker in the top-right corner shows which environment you are in. Always confirm it says Learning (or your Developer Plan environment) before building anything.

Words you learned today
  • Cloud — computers you use over the internet through a browser.
  • Browser / tab / URL / incognito — the program / one open site / a site address / a no-memory window.
  • Microsoft Entra ID — the identity system that manages all users in a tenant.
  • Tenant / environment / solution — the whole space / a room inside it / a box of components.
  • Maker portal — make.powerapps.com, your main workshop.
  • Environment picker — the top-right selector that tells Power Apps which room you're working in.
Real world — how enterprises use this

Large organisations use this exact cloud setup to build hundreds of internal tools:

  • A hospital system uses a canvas app (built by nurses, not IT) to capture patient intake data — replacing paper forms. The data flows into a Power BI dashboard for administrators in another environment.
  • A retail chain keeps separate environments per country — Dev (building), UAT (user testing), Production (live). One tenant; data isolated per environment.
  • A manufacturing company triggers a safety alert flow whenever a sensor reading exceeds a threshold — no code, just Power Automate checking an API on a schedule.

The tenant → environment → solution hierarchy you just learned is exactly what enterprise solution architects draw in whiteboard sessions. You already think like one.

Common mistakes on Day 1
  • Building in the wrong environment. The picker defaults to the company default environment — often a shared production space. Always switch to Learning first. Creating tables in the wrong environment can break live apps others are using.
  • Signing in with a personal Microsoft account. If a personal @outlook.com account is saved in the browser, Power Apps may use that. Always use incognito, and double-check the account shown in the top-right corner.
  • Confusing tenant with environment. "Our tenant" = the whole company's cloud space. "Our environment" = one isolated container inside it. A single tenant can have hundreds of environments.

Day 2

Dataverse: tables, columns, rows, and data types

~100 minutes

Concept — a database is like a very strict spreadsheet

If you have seen an Excel spreadsheet, you already understand 80% of this:

  • A table is like one sheet — it holds one kind of thing (e.g. all your Books).
  • A column (also called a field) is one piece of information about that thing (Title, Pages, Genre).
  • A row (also called a record) is one actual thing — the specific book called "Matilda".

The difference from Excel: each column has a fixed data type (enforced), tables can link to each other, and access is controlled by security roles. Dataverse is the Power Platform's built-in database — always on, no server to manage.

Concept — every data type and when to use it

When you add a column, you pick a type. Here are all the types you will use across this course:

  • Text — short words or sentences (names, codes, titles). Max length is settable.
  • Multiline Text — long text like descriptions, notes, or biography. Appears as a text area.
  • Whole Number — counts with no decimal (Pages, Quantity). Good for integers only.
  • Decimal Number — numbers with decimals (ratings, percentages). Use Currency instead for money.
  • Currency — money. Stores value + currency symbol. Use for Late fee, Price.
  • Date Only — just a date, no time. Use for Loan date, Due date, Born.
  • Date and Time — date plus a specific time. Use for meeting times, timestamps.
  • Choice — a fixed pick-list you define (Genre: Fiction / Science / Children…). Good for a small, stable set of options.
  • Lookup — a pointer to a row in another table. Like a dropdown showing real rows. Use for Author (lookup to Author table).
  • Yes/No — a true/false switch (In stock, Returned, Active).
  • Email — text that validates as an email address and shows as a clickable link.
  • Phone — text formatted as a phone number.
  • URL — text that validates as a web address and shows as a clickable link.
  • Image — stores a picture (e.g. book cover photo).
  • File — stores a binary file attachment.

Also important: Required vs Optional — a Required column cannot be saved blank. Set it for essential fields like Title. Default value — fills in a value automatically (e.g. In stock defaults to Yes, Available copies defaults to 1). Description — a note on the column for other developers to read.

Words you learned today
  • Dataverse — the Power Platform's built-in, always-on database.
  • Table / column (field) / row (record) — a kind of thing / a piece of info about it / one actual thing.
  • Data type — the kind of value a column holds (Text, Number, Choice, Lookup, Yes/No…).
  • Primary column — the main name column for each row (always required).
  • Required / Default value — cannot be left blank / fills in automatically.
  • View — a saved, filtered, sorted list of rows in a table.
  • Logical name — the system name used in formulas and filter expressions.
Real world — how companies design Dataverse data models

When professional Power Platform developers join a project, the first thing they do is model the data. A well-designed data model can support an app for 10 years; a bad one requires constant rework. Real patterns you'll see:

  • A field service company has a Work Order table (one per job), linking to Customer, Technician, Asset, and Parts Used tables. The Work Order is their "Loan" equivalent — the event table linking everything else.
  • A bank has a Case table with a Choice column for Status (Open / In Review / Resolved / Closed) — exactly like your Loan Status column.
  • An HR system stores employees in a Contact table with a Yes/No column called Active and a Choice column for Employment type — exactly like your Member table's Active and Membership fields.

The patterns are universal. Your Community Library data model IS how real enterprise apps are built.

Common mistakes when designing tables
  • Using Text for everything. If you store "240" as text instead of Whole number, you can't sort it numerically (10, 100, 2 will sort before 240 alphabetically) and can't do maths on it in flows.
  • Not setting Required on primary columns. Without Required on Title, someone can save a blank book row — your gallery will then show empty cards with no text.
  • Using Whole Number for phone numbers. Phone numbers start with 0 (e.g. 0812...). Integers drop leading zeros. Always use Text for phone, ISBN, and postal codes.
  • Creating a new table when a column is enough. If "Genre" only needs a label (Fiction, Science), use a Choice column. A whole Genre table is overkill unless genres have their own properties (description, icon, policy rules).

Day 3

Linking data: relationships, lookups, and the full data model

~110 minutes

Concept — why relationships matter (store each fact once)

Imagine every book stored the author's country and birth year. If an author wrote 10 books, you'd type their details 10 times — and have to fix 10 rows when something changed. The solution: store each author once in an Author table, then point each book to the right author. That pointing is a relationship — the core idea of good data design.

The pattern: one Author can relate to many Books. This is called one-to-many (1:N). The lookup column lives on the "many" side (the Book table holds a pointer to its Author). There are also many-to-many relationships — for example, a Book can have many Authors, and an Author can write many Books — but we won't need that complexity here.

Concept — choice vs lookup (when to use which)
  • A Choice is a pick-list of fixed words you decide in advance (Genre: Fiction / Non-fiction…). The options are part of the column design. Use for small, stable lists where each option has no extra details.
  • A Lookup points to a row in another table (Author lookup shows you Author rows). The options are live data that grows as you add rows. Use when the options have their own properties (name, country, biography).

Rule of thumb: short fixed list → Choice. A "thing" with its own record → Lookup.

Concept — cascading deletes: Restrict vs Cascade

When you link two tables, Dataverse asks what happens if you delete the "one" side. Two options:

  • Restrict — refuse to delete an Author if they still have Books pointing to them. Protects data integrity. Use this for important lookups (deleting Roald Dahl should fail because Matilda still exists).
  • Cascade — delete the Author and also delete all their Books automatically. Dangerous unless you're sure. Used for cleanup scenarios (deleting a Member auto-deletes their Loans).

For this course, use Restrict on Author→Book. Use the Dataverse default for Member→Loan (which is Restrict — safe).

Store each fact once, link with lookups.
Words you learned today
  • Relationship — a link between two tables; one side is "one", the other is "many".
  • One-to-many (1:N) — one Author can have many Books; the lookup lives on the "many" side.
  • Lookup column — a column that points to a row in another table; appears as a dropdown in forms.
  • Choice (option set) — a fixed pick-list defined in the column design.
  • Restrict / Cascade — two delete behaviors: block delete if children exist / delete children automatically.
Real world — data modelling in practice

Your four-table model (Author → Book ← Loan → Member) is a classic pattern called a transactional data model. It appears everywhere:

  • E-commerce: Customer → Order → OrderLine ← Product. OrderLine is the Loan equivalent — the linking event table.
  • Healthcare: Patient → Appointment ← Doctor. Appointment links two "dimension" tables to one event.
  • Banking: Account → Transaction ← MerchantCategory. Every transaction links an account to a category.

Understanding the difference between dimension tables (Author, Book, Member — the "what") and event/fact tables (Loan — the "what happened") is a skill that transfers from Dataverse to SQL to Power BI to any data platform. You are building the mental model now, at Day 3 of 20.

Common mistakes with relationships
  • Putting the Lookup on the wrong side. The Lookup always goes on the "many" side (Book has a Lookup to Author, not Author has a Lookup to Book). If Author had a Lookup to Book, each author could only have one book.
  • Using a text field for related data. Typing "Roald Dahl" as text in a Book row isn't a relationship — it's just a string. If Roald Dahl's name changes in the Author table, the book's text field doesn't update. A Lookup column is the only true link.
  • Forgetting to add rows to the Loan table for testing. If Loan has no rows, your Power BI report (Phase 6) will be blank and all DAX measures return 0. Add at least 10 diverse loan rows now — overdue, returned, and open — so your reports are meaningful.

Day 4

Keeping it tidy: solutions, security roles, environment variables

~90 minutes

Concept — a solution is a moving box for your whole project

As you build tables, apps, and flows, they can scatter across the environment. A solution is a labelled box you put related things into. Benefits:

  • Organisation — find everything in one place.
  • Portability — export the whole box as a .zip file, import it into another environment. This is how professionals ship software from Dev → Test → Production.
  • Backup — that .zip is also your safety copy (Day 16 walks through exporting it).

When you add an existing table to a solution, Dataverse references it — the table data isn't duplicated. New components you create inside the solution automatically belong to it.

A solution has a publisher with a short prefix (e.g. learn). Every new column you create inside the solution gets that prefix on its logical name: learn_isbn. This prevents name clashes when multiple solutions from different publishers live in the same environment.

Concept — security roles (who can do what)

A security role is a collection of permissions: can this person create, read, update, or delete rows in each table? Permissions also have scope: their own rows only (User), their business unit (Business Unit), or everyone (Organisation).

  • System Administrator — can do everything. Give this to yourself in the Learning environment (it's an isolated practice room, so there's no risk).
  • Basic User — can use apps and read/write data they're allowed to. Give this to people using the finished app.

In the real world: a library staff member would get a custom role with read/write on Book and Loan but no access to admin settings.

Concept — environment variables (stored settings)

An environment variable is a named, typed value stored at the environment level — separate from any app or flow. When the value changes (e.g. the loan period changes from 14 days to 21 days), you update the environment variable in one place and every flow that reads it automatically uses the new value. No editing individual flows.

Types: Text, Number, Boolean (true/false), JSON (structured data), Data source (a connection reference), Secret (stored securely in Key Vault).

Each variable has a default value (set at design time) and an optional current value (set per environment, overrides default). This lets you have different values in Dev vs Production without editing your flow.

Words you learned today
  • Solution — a movable box grouping related tables, apps, and flows.
  • Publisher / prefix — the solution's owner identity / the short code added to new column logical names.
  • Managed / unmanaged — locked (deployable) vs editable (in-progress) solution.
  • Security role — a set of table-level permissions scoped to user / business unit / org.
  • Environment variable — a named, typed setting stored at environment level; read by flows and apps.
  • Default value / current value — the design-time fallback / the per-environment override.
Real world — solutions in enterprise Power Platform

In enterprise deployments, solutions are the unit of work — every change is tracked inside a solution and moved between environments as a managed package. Real examples:

  • A global bank maintains 12 separate solutions in one environment — each for a different business domain (HR, Finance, Compliance). Teams don't interfere with each other's components because each solution uses a different publisher prefix.
  • A retailer's "ALM pipeline" automatically exports the Dev solution as managed every night, imports it into Test, runs automated tests, and deploys to Production on Friday — no human steps after the initial setup.
  • Environment variables are the mechanism that makes this possible: the database connection string, the email address for alerts, and the API endpoint are all environment variables. Dev, Test, and Production each have their own current values for those variables, but the flow code never changes.
Common mistakes with solutions
  • Building outside the solution. If you create an app from the Apps menu instead of from Solutions → My Learning Solution → New, that app won't be in the solution. You'll be unable to export it as part of the solution package. The fix: add existing components to the solution after the fact — but this is easy to forget. Build from inside the solution from now on.
  • Skipping environment variables for config. Hardcoding a value like "14" for loan days directly in a flow means you must edit the flow to change it. Always store configurable values in environment variables.
  • Exporting unmanaged to production. An unmanaged solution can be edited in the target environment — removing the separation between Dev and Prod. Always export managed for Test and Production deployments.
