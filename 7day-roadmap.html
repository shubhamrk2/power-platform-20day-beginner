Full Keyword Glossary

28 terms defined in plain English, every one with a library example. These are the words you must own before any Power Platform interview.

Power Platform

Microsoft's low-code suite of five tools: Power Apps (build UIs), Power Automate (workflows), Power BI (reports), Power Pages (public websites), and Copilot Studio (AI chatbots). They all plug into Dataverse and share the same licensing, connectors, and admin center. For this library project, you use Apps, Automate, and BI.

Environment

An isolated container — think of it as a separate room — that holds its own apps, flows, Dataverse tables, and data. You have three: LM-DEV (you build here), LM-UAT (test users test here), LM-PRD (live members use here). Nothing in one environment can accidentally break another. Rohit Verma testing in UAT never touches DEV data.

Dataverse

Microsoft's managed cloud database built specifically for Power Platform. Think of it as SQL Server but with built-in security roles, audit logs, relationships, and business rules — and no server to manage. Your Books, Members, and Loans tables all live in Dataverse inside LM-DEV. Unlike SharePoint lists, Dataverse supports proper relational lookups, currency fields, and row-level security.

Table

The Dataverse equivalent of a database table — a structured collection of rows all sharing the same columns. You create three tables: Books, Members, and Loans. Tables have two kinds: Standard (built-in, like Contact or Account) and Custom (ones you create, like your Books table). Custom tables get a publisher prefix on every column name.

Column

A single field inside a table — the equivalent of a spreadsheet column. Examples: cr_title (Text) on Books, cr_email (Email) on Members, cr_late_fee (Currency) on Loans. Column types include Text, Number, Date, Choice (dropdown), Lookup (link to another table), Yes/No, Currency, and File. The type you choose affects what Power Fx functions you can use on it.

Row

One record in a table — all the data about one thing. Rohit Verma's loan of The Alchemist is one row in the Loans table, containing: Rohit's member lookup, the book lookup, loan_date = 2025-01-05, due_date = 2025-01-19, returned = Yes. When you use Patch() in Power Fx, you're creating or updating a row. When you use Filter(), you're selecting certain rows.

Publisher

A prefix attached to every custom table, column, and component name to avoid naming conflicts. You create a publisher with prefix cl for this project. Dataverse automatically names your columns cl_title, cl_email, etc. The default out-of-the-box publisher uses prefix cr (which is why you see cr_ everywhere in Microsoft docs — if you created components without switching publishers). Always use your own publisher prefix in real projects.

Solution

A deployment container that packages all your components — apps, flows, tables, security roles, environment variables — into a single transportable zip. Solutions are how you move your work from DEV to UAT to PRD. There are two types:

Unmanaged — the "editable" state you work in inside LM-DEV. All components are modifiable. You export as Unmanaged to back up your work.

Managed — the "locked" state you import into LM-UAT and LM-PRD. Nobody can directly edit apps or flows in a managed environment. Changes must come from re-deploying from DEV. This enforces ALM discipline.

Canvas App

A Power Apps type where you design every pixel of the UI yourself — like designing slides in PowerPoint but with live data. You add screens, galleries, buttons, and text inputs exactly where you want them. You write Power Fx formulas on each control's properties. In this project, the Member Borrowing Portal is a canvas app — Rohit Verma sees a browse screen with a search box and a gallery of book covers.

Model-Driven App

A Power Apps type where the UI is automatically generated from your Dataverse table schemas — you don't position controls manually. You configure views (which columns to show), forms (which fields to edit), and navigation. Model-driven apps are ideal for staff working with complex data relationships. In this project, Sanjay Singh uses the Library Staff Portal (model-driven) to manage all loans, members, and books.

Power Fx

The Excel-like formula language used inside canvas apps. If you know =VLOOKUP() in Excel, Power Fx is the same idea but for live Dataverse data. Key functions: Filter() to query rows, Patch() to create/update, Navigate() to switch screens, Notify() to show messages, If() for conditions, Set() for variables. Power Fx is NOT used inside Power Automate flows — flows use Expressions instead.

Connector

A pre-built API wrapper that connects Power Platform to an external service — Outlook, SharePoint, SQL Server, Teams, HTTP, and 1,000+ others. You don't write REST calls; Microsoft wrote the wrapper. Two types:

Standard — free with any Power Platform license. Examples: SharePoint, Outlook (Office 365), Teams, Excel Online, OneDrive.

Premium — requires Power Apps/Automate Per User plan or Developer Plan. Examples: HTTP, Dataverse (direct connection in flows), SQL Server, Salesforce. Ashwini's Developer Plan covers all premium connectors.

Connection

One authenticated instance of a connector. A Connection Reference points to a Connection. When Neha Agarwal's Outlook Connection is used in a flow, that's one Connection — tied to her specific email account. If you deploy the same flow to UAT, you need a new Connection (Ashwini's UAT Outlook) because the credentials change between environments. Connections are environment-specific; Connection References are solution-portable.

Connection Reference

A named placeholder inside a solution that points to a Connection, allowing the connection to be swapped per environment without changing any app or flow code. Example: Your flow has a Connection Reference called CL_Outlook_Ref. In LM-DEV it points to Ashwini's DEV Outlook connection. When you import the managed solution to LM-UAT, you re-map CL_Outlook_Ref to a UAT Outlook connection — the flow code is untouched. Without Connection References, deploying across environments breaks every connector.

Environment Variable

A solution-level variable that holds a value which can differ per environment. You reference the variable name in code; the actual value is set at import time. Example: cl_LoanPeriodDays = 14 in LM-DEV (generous for testing), = 7 in LM-PRD (library policy). Your canvas app reads the variable — same code, different behavior per environment. Without Environment Variables, you'd have to hard-code different values for each environment, which defeats the purpose of managed solutions.

ALM — Application Lifecycle Management

The discipline of moving your application through structured stages: DEV (build & unit test) → UAT (user acceptance test) → PRD (production, live users). In Power Platform, ALM is implemented by exporting a Managed solution from DEV and importing it to UAT/PRD, or by using Power Platform Pipelines to automate that. ALM prevents "cowboy changes" — direct edits to production that can't be tracked or rolled back.

Pipeline (Power Platform Pipelines)

A free, built-in tool that automates the DEV→UAT→PRD deployment with a single Deploy button click inside make.powerapps.com. No manual export/import zip file. You configure the pipeline once (which environments, in what order), then each deployment is one click and creates an audit trail. Available from the Pipelines section of a solution. This is the modern ALM approach; manual export/import is the fallback when Pipelines aren't available.

DLP — Data Loss Prevention

Admin-controlled policies (created in the Power Platform Admin Center) that restrict which connectors can work together in a single flow or app. You group connectors into Business (allowed) and Non-Business (blocked from mixing with Business). Example: DLP can block the HTTP connector from being used alongside SharePoint — preventing someone from building a flow that copies SharePoint data to an unknown external URL. DLP is set by admins; developers can't override it. Only Pooja Sharma (Library Admin) can create DLP policies.

Business Rule

A no-code condition-and-action attached directly to a Dataverse table or form. Business Rules run without a flow and without writing code. Example: If cr_membership_type = Student, show a warning message "Student limit: 2 books." Business Rules can set field values, show/hide fields, enable/disable fields, and validate data — but only on the form level, not in background batch operations (use flows for that).

Security Role

A Dataverse permission set that defines what a user can Create, Read, Update, or Delete on each table, and at what scope (their own rows, their business unit's rows, or all rows). You create four roles: Library Member (read Books, CRUD their own Loans), Junior Librarian (CRUD Books, read Members, read/write Loans), Senior Librarian (all of Junior + write Members), Library Admin (full CRUD everywhere). Security Roles live in the environment and are assigned per-user in the Admin Center.

Row-Level Security (RLS)

A pattern that ensures each user sees only the data rows that belong to them. In canvas apps, you implement this with a Power Fx filter: Filter(Loans, 'cr_member (Members)'.cr_email = User().Email). When Priyanka Singh logs in, User().Email returns her email — so she only sees her own loans. Mohammed Khan's loans are invisible to her. Dataverse Security Roles also enforce RLS at the database level (ownership scope), giving you two layers of security.

Trigger

The event that starts a Power Automate flow. There are three types: Automated — triggered by an event (e.g. "When a row is added to Loans"); Scheduled — runs on a timer (e.g. "Every day at 9:00 AM"); Instant — started manually, by a button in an app, or by a parent flow calling a child flow (this is the trigger child flows must use). You cannot mix trigger types — each flow has exactly one trigger.

Action

A single step inside a flow that does something after the trigger fires. Examples: Get a row by ID (reads one Dataverse record), Send an email (V2) (Outlook), Condition (if/else branch), Apply to each (loop over a list), Compose (compute an expression), Run a child flow. A flow is just a trigger plus a sequence of actions. Actions run top-to-bottom; you can use outputs from earlier actions in later ones via Dynamic Content.

Child Flow

A flow designed to be called by another flow (the parent). It must use "Manually trigger a flow" as its trigger, with defined input parameters. At the end, it uses "Respond to a PowerApp or flow" to return output values. It must be inside the same solution as its parent. Child flows promote reuse: your "Calculate Late Fee" logic is written once and called from both the Return Book parent flow and the Scheduled Audit flow.

Parent Flow

A flow that calls one or more child flows using the "Run a child flow" action (found under the Flow connector in Power Automate). The parent passes input parameters to the child and receives output parameters back. The parent can call multiple child flows sequentially. In this project, CL - Process Book Return (Parent) calls two child flows: one to calculate the late fee, one to send the confirmation email.

Expression

The formula language used inside Power Automate actions — completely different from Power Fx used in canvas apps. Expressions use Azure Logic Apps / Workflow Definition Language syntax. Examples: addDays(utcNow(), 14) adds 14 days to today; formatDateTime(utcNow(), 'dd MMM yyyy') formats a date; mul(3, 5) multiplies. You write expressions in the fx field of an action. Don't confuse with Power Fx — they're separate languages.

Respond to a PowerApp or flow

The action placed at the end of a child flow (or a flow called by a canvas app button) to return output values back to the caller. Without this action, the parent flow gets no data back from the child. You define named outputs with types (Text, Number, Boolean). The parent flow then receives these outputs via Dynamic Content — for example, the child returns fee_amount = 15, and the parent uses that number to update the Loan record's cr_late_fee column.

Admin Center (PPAC)

The Power Platform Admin Center at admin.powerplatform.microsoft.com — the control panel for admins. From here: create and manage environments (LM-DEV, LM-UAT, LM-PRD), create DLP policies, monitor capacity and storage, add users to environments with environment roles (System Admin or Basic User), view analytics, and manage Dataverse security. Pooja Sharma (Library Admin + System Administrator) spends most of her time here, not in make.powerapps.com.

Environment Setup + Dataverse Foundations

Goal: Create your LM-DEV environment, set up a Solution with a custom publisher, build the Books / Members / Loans tables, and import all three CSV files so the library database is ready to build on.

Environment Dataverse Table Column Row Publisher Solution Admin Center

Concepts

The Admin Center and make.powerapps.com are two different portals with different jobs. The Admin Center (admin.powerplatform.microsoft.com) is where environments are created and managed. The maker portal (make.powerapps.com) is where you build apps and flows. You start every working session by switching to the correct environment in the maker portal — the environment selector is a dropdown in the top-right corner.

A Solution is your project's container. Every app, flow, table, and environment variable you create must be inside the solution — components created outside a solution can't be deployed via ALM. The Publisher prefix (cl for Community Library) is stamped on every custom column name: cl_title, cl_email, cl_due_date. This prevents naming collisions with Microsoft's own system columns.

Dataverse relationships work via Lookup columns. A Lookup from Loans to Books means each loan row carries a reference to exactly one book row — Dataverse enforces referential integrity automatically. When you read a lookup value in Power Fx, you use dot notation: ThisItem.'cl_book (Books)'.cl_title.

End-of-Day Checkpoint

Q: What is the difference between a Column of type Lookup and a Column of type Choice?

See answer

Choice — a predefined list of options stored in the column definition itself (e.g. Membership type: Premium / Standard / Senior / Student). The options are fixed; users pick from a dropdown. Data stays in the same table.

Lookup — a link to a row in a different table. The Loans table's cl_book column is a Lookup to the Books table — it stores the ID of one Books row, not a copy of the book title. When you read the loan, Dataverse fetches the book title from the Books table automatically. This creates a real relational link; if you edit the book title in Books, the Loans view immediately reflects the new title.

Day 2

Canvas App — Member Borrowing Portal

Goal: Build a 3-screen canvas app where members browse available books, borrow a book with one tap, and see only their own active loans — implementing row-level security in Power Fx.

Canvas App Power Fx Row-Level Security Connection

Concepts

A canvas app is structured as screens. Each screen contains controls (Gallery, Button, TextInput, Label, Form). Every control has properties — things like Items, Text, Visible, OnSelect — and each property accepts a Power Fx formula. The formula bar at the top works exactly like Excel: you click the property in the dropdown, type your formula, and the control reacts live.

User().Email is the magic function for row-level security. It returns the M365 email of whoever is currently logged in. When you write Filter(Loans, 'cl_member (Members)'.cl_email = User().Email) on a gallery's Items property, Dataverse only returns loans where the member's email matches the logged-in user. Priyanka Singh logs in → gets her loans only. Mohammed Khan logs in → gets his loans only. Same app, different results, zero extra code.

The Patch() function writes data back to Dataverse. Patch(Loans, Defaults(Loans), {...}) creates a new row. Defaults(Loans) tells Power Fx to start with all default values for the Loans table. You then override specific columns in the second argument using column names as keys.

Step-by-Step Tasks

  1. Inside your solution → New → App → Canvas App → Name: Library Member Portal → Format: Tablet
  2. Set App.OnStart to: Set(CurrentMember, LookUp(Members, cl_email = User().Email)) — this stores the logged-in member's full record in a global variable
  3. Rename Screen1 to BrowseScreen. Add a Vertical Gallery → Data source: Books → set Items to: Filter(Books, cl_available = true)
  4. Add a TextInput named SearchInput above the gallery. Update gallery Items to: Search(Filter(Books, cl_available = true), SearchInput.Text, "cl_title", "cl_author")
  5. Inside the gallery template, add Labels for Title (ThisItem.cl_title), Author (ThisItem.cl_author), and a Genre badge (ThisItem.cl_genre). Add a Navigate button: Navigate(DetailScreen)
  6. Add Screen2, rename to DetailScreen. Add Labels showing BookGallery.Selected.cl_title, BookGallery.Selected.cl_author. Add a Borrow button
  7. Set Borrow button OnSelect:

  9. Add navigation buttons: BrowseScreen → MyLoansScreen, MyLoansScreen → BrowseScreen. Add a Back arrow on DetailScreen

End-of-Day Checkpoint

Q: Why does User().Email return different values for Priyanka Singh vs Mohammed Khan when they use the same app?

See answer

User().Email calls Microsoft's identity service at runtime and returns the email of whoever is currently authenticated in the app. The app itself doesn't store a username — it asks the platform "who is logged in right now?" Power Platform enforces one active session per browser/device. So when Priyanka opens the app, User().Email = priyanka.singh@gmail.com. When Mohammed opens the same app on his device, User().Email = mohammed.khan@email.com. Same formula, different caller, different result — that's how session-based row-level security works without any code change.

Day 3

Power Fx Deep Dive — Validation, Variables & Calculated Fields

Goal: Add loan-limit enforcement, overdue visual indicators, dynamic form modes, and a running fine total — making the app smart enough to prevent rule violations automatically.

Power Fx Business Rule Row-Level Security

Concepts

Variables in Power Fx come in two forms: global (Set(varName, value) — accessible from any screen) and context (UpdateContext({varName: value}) — scoped to the current screen only). You use Set(ActiveLoanCount, CountRows(...)) because the count is needed on multiple screens. Context variables are better for temporary UI state like "is this form in edit mode?"

Filter() returns a table — multiple rows. LookUp() returns a single record — the first row that matches. Use Filter() when you need a list (gallery items, countrows). Use LookUp() when you need one specific record (find the current member, find one book by ISBN). Mixing them up is the #1 beginner mistake in Power Fx.

DateDiff(date1, date2, unit) returns a positive number if date2 is after date1. For overdue detection: DateDiff(Today(), ThisItem.cl_due_date, Days) — if this is negative, the book is overdue. You use this in an If() to color the row red or green.

Step-by-Step Tasks

  1. On BrowseScreen OnVisible, set the active loan count: Set(ActiveLoanCount, CountRows(Filter(Loans, 'cl_member (Members)'.cl_email = User().Email && cl_returned = false)))
  2. Set Borrow button Visible to: ActiveLoanCount < Switch(CurrentMember.cl_membership_type, "Premium", 10, "Senior", 5, "Standard", 3, "Student", 2) — Premium can borrow 10, Student only 2
  3. Add a Label below Borrow button with Text: If(ActiveLoanCount >= 2 && CurrentMember.cl_membership_type = "Student", "Loan limit reached (Student max: 2)", "")
  4. In MyLoansScreen gallery template, set the background color of the due-date label to: If(DateDiff(Today(), ThisItem.cl_due_date, Days) < 0, RGBA(248,81,73,0.15), RGBA(63,185,80,0.1)) — red if overdue, green if within date
  5. Add a due-date icon: If(DateDiff(Today(), ThisItem.cl_due_date, Days) < 0, "⚠ OVERDUE", "Due: " & Text(ThisItem.cl_due_date, "dd mmm yyyy"))
  6. Add a "Total fines" label on MyLoansScreen — see formula block below
  7. For the Loan Form on DetailScreen, set Mode to: If(IsBlank(BookGallery.Selected), FormMode.New, FormMode.View)
  8. Add a membership tier badge on BrowseScreen using Switch for color: Switch(CurrentMember.cl_membership_type, "Premium", RGBA(227,179,65,1), "Senior", RGBA(248,81,73,0.8), "Student", RGBA(88,166,255,1), RGBA(63,185,80,1))

End-of-Day Checkpoint

Q: What is the difference between Filter() and LookUp() in Power Fx?

See answer

Filter(Table, Condition) — returns a Table (zero or more rows). Use it when you need a list: gallery items, CountRows(), Sum() across multiple records. Example: Filter(Loans, cl_returned = false) returns all open loans.

LookUp(Table, Condition, Result) — returns a single Record (the first match). Use it when you need one specific thing. Example: LookUp(Members, cl_email = User().Email) returns the one member record for the logged-in user. If you try to use Filter() where a single record is expected (like setting a Lookup field in Patch()), you'll get a type mismatch error.

Day 4

Power Automate — Flows, Child Flows & Parent Flows

Goal: Build a scheduled overdue reminder flow, then architect a parent-child flow system that calculates late fees and sends return confirmations — the most important flow pattern you'll use in real projects.

Trigger Action Child Flow Parent Flow Expression Respond to a PowerApp or flow Connector Connection Reference

Concepts

Power Automate flows are built from a trigger (what starts the flow) and a sequence of actions (steps that do things). Expressions inside actions use a different formula language from Power Fx — they use Azure Logic Apps syntax like addDays(utcNow(), 14), formatDateTime(), mul(), div(). You write expressions inside an action's fx field.

Child flows are the Power Automate equivalent of a reusable function. Instead of copy-pasting the same 5-step late-fee logic into three different flows, you write it once as a child flow and call it from anywhere. The key rules: child flows use Manually trigger a flow as their trigger, they define typed inputs, and they return outputs via Respond to a PowerApp or flow. Both parent and child must be in the same solution.

The Run a child flow action is found under the Flow connector (search "Run a child flow" in the action search bar). After the action completes, the child flow's outputs appear in the Dynamic Content panel of the parent — you can reference them in subsequent actions just like any other output.

Part A

Daily Overdue Reminder (Scheduled Flow)

  1. In your solution → New → Automation → Cloud Flow → Scheduled. Name: CL - Daily Overdue Reminder. Set: every 1 Day at 09:00 AM IST
  2. Add action: List rows (Dataverse). Table: Loans. Filter rows: cl_returned eq false and cl_due_date lt @{utcNow()}. This returns all loans that are unpaid AND past due date
  3. Add action: Apply to each. Input: the value output from List rows (this loops over each overdue loan)
  4. Inside Apply to each → Add action: Get a row by ID (Dataverse). Table: Members. Row ID: the cl_member lookup value from the current loan row (use Dynamic Content)
  5. Inside Apply to each → Add action: Send an email (V2) (Outlook). To: member's cl_email. Subject: Overdue book reminder — @{items('Apply_to_each')?['cl_book_name']}. Body: "Hi [member name], your copy of '[book title]' was due on [date]. Late fee: ₹5/day. Please return it at the earliest."
  6. Save the flow. Turn it On

Interview Q & A — Parent Flow calling a Child Flow

Q: If asked to create a simple parent flow that calls a child flow, walk me through your approach step by step.

  1. Build the child flow first. Use "Manually trigger a flow" as the trigger — this is mandatory, not optional. Define all input parameters in the trigger (e.g. DueDate as Text, LoanID as Text). Add your logic steps (Compose, Condition, HTTP, etc). At the very end, add "Respond to a PowerApp or flow" and define every output the parent will need (e.g. fee_amount as Number). Save and note the flow's name exactly.
  2. Both flows must live in the same solution. If the child is not in the same solution, the "Run a child flow" action will not find it. This is the most common mistake beginners make.
  3. Build the parent flow. Choose any trigger (PowerApps, Scheduled, or Automated — child flows don't care). Find the action "Run a child flow" under the Flow connector. Select your child flow from the dropdown. The child flow's input parameters appear as fields — map values from Dynamic Content or Expressions. After the action completes, the child flow's output values appear in the Dynamic Content panel for all subsequent parent actions.
  4. The child flow cannot see the parent's context automatically — you must explicitly pass everything the child needs as input parameters. Design child flows to be self-contained and reusable.
  5. Why use child flows? The "Calculate Late Fee" logic is identical whether a member returns a book (Return button), a librarian processes a return (Staff Portal), or a scheduled job audits overdue accounts. Write the child flow once, call it from all three parent flows — changes to fee rules happen in one place only.

Key constraint to remember: Child flows cannot recurse (call themselves). They also cannot call sibling child flows — only a parent can call a child.

End-of-Day Checkpoint

Q: What trigger type must a child flow use? Why can't you use "When a row is added" as a child flow trigger?

See answer

A child flow must use "Manually trigger a flow" as its trigger. This is because the parent flow calls the child flow directly — it doesn't fire an event or add a row. The "Manually trigger a flow" trigger is the only one that supports defined input parameters and can receive calls from a "Run a child flow" action.

"When a row is added" is an Automated trigger — it's woken up by a Dataverse event, not by another flow. It has no input parameters for the parent to pass data through. If you tried to use it as a child, the "Run a child flow" action wouldn't find it in the dropdown because Power Platform only lists flows with "Manually trigger a flow" triggers as valid child flows.

Interview Q & A — 10 Essential Questions

Click "See answer" to reveal each answer. Practice saying these out loud.

Q1

Canvas App vs Model-Driven App — when do you use each?

See answer

Canvas App when: users need a custom, pixel-perfect UI (mobile-first, consumer-facing, specific branding); when data comes from multiple sources (SharePoint + SQL + Dataverse in one screen); or when the user interaction is non-standard (custom workflows, kiosk screens). Example: the Member Borrowing Portal — members need a clean, app-like experience.

Model-Driven App when: users are staff working with complex relational data where the standard form/list/detail pattern is sufficient; when you need built-in timeline, Business Rules, and audit logs without extra effort; when data is entirely in Dataverse. Example: the Library Staff Portal — Sanjay Singh needs to manage hundreds of loans and members efficiently, not beautifully.

One-liner: Canvas = creative control for custom UX; Model-driven = productivity for data-heavy back-office work.

Q2

What is ALM in Power Platform? How do you implement it?

See answer

ALM stands for Application Lifecycle Management — the practice of moving your app through structured stages: DEV (build) → UAT (test) → PRD (live). Without ALM, you make changes directly in production, can't roll back, and have no audit trail.

In Power Platform, ALM is implemented by: (1) keeping all components inside a Solution, (2) exporting the solution as Managed from DEV, (3) importing the managed solution to UAT/PRD. Alternatively, use Power Platform Pipelines (free built-in tool) for one-click deployment with automated steps. Connection References and Environment Variables are the technical enablers that allow the same solution to work across all three environments without code changes.

Q3

What is a Connection Reference and why is it needed?

See answer

A Connection Reference is a named placeholder inside a solution that points to a connector connection. Instead of a flow directly using "Ashwini's Outlook connection" (which only exists in LM-DEV), the flow uses "CL Outlook Reference" — a pointer that can be re-mapped to a different connection at import time.

Without it: import your solution to LM-UAT and every Outlook/Dataverse action in every flow breaks immediately, because those specific connections don't exist in UAT. With it: during import, you map the reference to a UAT-specific connection — the flow code is unchanged. This is how you make solutions portable across environments.

Q4

Managed vs Unmanaged Solution — what's the difference?

See answer

Unmanaged — the working state in DEV. All components are editable. Deleting a component from the solution (not from the environment) doesn't delete the underlying app/table — it just removes it from the solution packaging. You can have multiple unmanaged solutions in one environment.

Managed — the deployed state in UAT/PRD. Components are locked — nobody can edit apps, flows, or tables directly. Deleting the managed solution deletes all its components from the environment (clean uninstall). When you re-import an updated managed solution, it layers over the existing one. This creates a clear separation: DEV is where you build, UAT/PRD is where you run — and the two never mix.

Q5

What are Environment Variables? Give a real example from this project.

See answer

Environment Variables are solution-level key-value pairs where the key is constant but the value is set per environment at deployment time. You reference the variable name in code — the runtime resolves it to the correct value for the current environment.

Real example: cl_LoanPeriodDays. In LM-DEV = 14 (generous for easy testing). In LM-UAT = 7 (closer to real policy). In LM-PRD = 7 (actual library rule). The canvas app's Borrow button formula reads LookUp('Environment Variable Values', ...) — same formula, different result per environment. No code changes between deployments. Other good candidates: fee per day (₹5 in DEV, ₹10 in PRD), library email sender address, max overdue days before membership suspension.

Q6

What is DLP? Who creates DLP policies and who is affected?

See answer

DLP (Data Loss Prevention) policies are admin-controlled rules that group connectors into tiers — Business (allowed to work together), Non-Business (isolated), and Blocked (cannot be used at all in a flow or app). If a flow tries to combine a Business connector (SharePoint) with a Non-Business one (HTTP to external), the DLP policy blocks the flow from running.

Who creates them: only Power Platform Administrators and Tenant-level Global Admins. Developers like Ashwini cannot create or override DLP policies. In this project, Pooja Sharma (Library Admin + System Admin) creates the "Library DLP" policy in the Admin Center, blocking HTTP in LM-UAT and LM-PRD to prevent unauthorized data exfiltration. DLP policies are the governance safety net — they enforce data boundaries even when developers don't know (or don't follow) security rules.

Q7 — Most Important

Walk me through creating a parent flow that calls a child flow, step by step.

See answer
  1. Design the child flow first. Decide what inputs it needs and what outputs it returns. In this project: inputs = DueDate, ReturnDate; output = fee_amount.
  2. Create the child flow. New → Instant cloud flow → trigger: Manually trigger a flow. Add all inputs via "Add an input" in the trigger. Add your logic actions. At the very end, add Respond to a PowerApp or flow and define all outputs.

Q8

What is the difference between a Trigger and an Action in Power Automate?

See answer

Trigger — the event that starts a flow. Every flow has exactly one trigger. Types: Automated (Dataverse row added/modified, email received), Scheduled (every day at 9 AM), Instant (button click, PowerApps call, "Manually trigger a flow" for child flows). The trigger also defines what input data is available to the flow — a "When a row is added" trigger provides the new row's data; a PowerApps trigger provides data passed from the app.

Action — a step inside the flow that does something: reads data, writes data, sends an email, evaluates a condition, loops over a list. A flow can have unlimited actions. Actions can use outputs from previous actions via Dynamic Content. Common actions: Get a row by ID, List rows, Send an email, Condition (if/else), Apply to each (loop), Compose (compute expression), Run a child flow.

Q9

How do you implement Row-Level Security in a Canvas App?

See answer

Two layers — and you should use both:

Layer 1 — Power Fx filter (app layer): On the gallery's Items property: Filter(Loans, 'cl_member (Members)'.cl_email = User().Email && cl_returned = false). User().Email returns the email of the currently logged-in user. This filters what is displayed in the UI.

Layer 2 — Dataverse Security Role (database layer): Assign the "Library Member" security role with Loans scope = User. This means even if someone bypasses the canvas app (e.g. calls the Dataverse API directly or uses Power Automate), they can only access their own loan rows. The database enforces ownership regardless of the application layer.

Layer 1 alone is UI-only security — savvy users could bypass it. Layer 2 alone doesn't help in canvas apps (the app delegates queries to Dataverse, which respects the role). Using both is the correct production pattern.
