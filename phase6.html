Concept — the two Power BI tools, and which to use

Power BI comes in two parts that work together:

  • Power BI Service — the website app.powerbi.com. Runs in your browser (so you can use it now). Where you share reports, make dashboards, and manage workspaces. You can also build simple reports here.

Plan for a beginner with no personal laptop: do everything you can in the Service (browser), and treat Desktop as the "when you have a Windows laptop" tool. Where a step is Desktop-only, this course says so and gives the browser alternative.

Day 17

Get started & get data

~110 minutes · Learn path: Get started with Power BI

Concept — what Power BI is for

Power BI connects to your data, lets you clean and model it without changing the source, helps you visualise what matters, and lets you share it. If a spreadsheet answers "what are the numbers?", Power BI answers "what do they mean, at a glance?" Every project follows four steps — and you already know the first two:

Concept — where data comes from (connectors)

Power BI can connect to hundreds of data sources through the Get data button: files (Excel, CSV), databases (SQL Server), online services, the web, and — importantly for you — Dataverse and SharePoint (the data you built earlier!). You pick a source, sign in if needed, and choose the tables you want.

Concept — dataset, report, dashboard
  • A dataset (or semantic model) is the prepared, linked data a report reads from.
  • A report is one or more pages of charts built on a dataset.
  • A dashboard (Service only) is a single screen pinning the most important visuals.
Your Power BI report uses YOUR project — not a new file This whole phase builds a report on the Loan data from your Community Library. Nothing new to invent: Loan is the fact (each borrowing), and Book, Member and Date are what you slice by.
Do this — get your project's data into Power BI
  • Best (Desktop): open Power BI Desktop → Get data → Dataverse → sign in to your Learning environment → load Loan, Book, Member. This connects Power BI straight to your project.
  • Browser-only alternative: use the Loan and Member Excel files you exported on Day 16 (plus a quick Books export). In app.powerbi.com → My workspace → New / Get data → Files → Local file → upload → Import. A dataset appears.
  • Choose Import (know when you'd use DirectQuery — see the tip below).
  • Open the built-in Sample report in the Service; click a bar and watch other charts react ("everything filters everything") to see where you're heading.
Tip — Import vs DirectQuery When you connect, you often choose a storage mode: Import copies a snapshot into Power BI (fast, most common, refreshed on a schedule); DirectQuery leaves data in the source and queries it live (for very large or always-fresh data, with some limits). For learning, choose Import.
Words you learned today
  • Data source / Get data — where data comes from / the button to connect.
  • Dataset / report / dashboard — prepared data / pages of charts / a one-screen summary.
  • Storage mode: Import vs DirectQuery — copy a snapshot in vs query live in place.
Real world — Power BI in enterprises

Power BI is the most widely deployed business intelligence tool in Microsoft's ecosystem. Real examples:

  • A global retailer has a Power BI dashboard showing live sales by store, region, and product category via DirectQuery — 50 million rows, always current, refreshed per user click.
  • A hospital imports daily patient data into Power BI (Import mode) refreshed at midnight. Every morning, executives see yesterday's occupancy rate, average stay, and readmission numbers on a Teams pinned dashboard.
  • A bank's compliance team uses Row-Level Security: each regional officer sees ONLY their region's flagged transactions — the same report, different data, secured with USERPRINCIPALNAME(). You'll build this on Day 20.

The four steps — get, clean, model, visualise, share — are the same whether your dataset has 10 rows or 10 billion. You're learning the pattern that scales.

Common mistakes on Day 17
  • Using DirectQuery when Import is enough. DirectQuery queries the source on every visual interaction — slow for complex models. Use Import unless you genuinely need live data. For most reports, a nightly refresh is fine.
  • Loading data to My workspace for sharing. My workspace is personal — others can't see it. Create a dedicated team workspace for shared reports.
  • Confusing dataset, report, and dashboard. Dataset = prepared data + DAX. Report = visual pages on a dataset. Dashboard = pinned highlights. Three separate objects — deleting a report does not delete the dataset.

Click any bar in a chart and watch all other visuals react — this cross-filtering is Power BI's most valuable interactive feature. Then click the slicer and select one store manager — all charts now show that manager's data only.
  • Exercise 2: Download the Retail Analysis Sample report as a .pbix (File → Download). If you have Power BI Desktop, open it. Click Model view — you'll see the star schema with dimension tables around a fact table. This is identical to your library model (Loan = fact, Book/Member = dimensions).
  • Exercise 3: Connect your library data: Desktop → Get data → Dataverse → Learning environment → select Loan, Book, Member. Or upload Excel exports to the Service. Confirm all three tables appear in the Data pane before proceeding to Day 18.
  • Exercise 4: In the Data pane, examine the raw Loan table. Which columns are date type? Which lookup columns appear as GUIDs? Note the GUID columns — these are what you'll replace with readable names by creating relationships on Day 19.
  • Exercise 5: In My workspace, create a new workspace (Workspaces → + New workspace). Name it Library Reports. This is where you'll move your finished report on Day 20. Keeping reports in a named workspace is how organisations manage shared content — My workspace is only for personal draft work.
Mini-quiz — Day 17

Q1 What is the difference between a Power BI dataset and a Power BI report?

Q2 You need a report that always shows real-time data from a 500GB SQL database. Which storage mode?

Q3 You delete a Power BI report. Does the underlying dataset also get deleted?

Show answers

A1 A dataset is the prepared data — tables, relationships, and DAX measures. A report is visual pages built on top of a dataset. One dataset can feed many reports; deleting a report doesn't delete the dataset.

A2 DirectQuery — it passes queries to the source in real time. Import would require a refresh every few seconds for a 500GB database, which isn't practical.

A3 No. The dataset remains as a separate object. You can build a new report on the same dataset without re-importing the data.

Check yourself Name the four steps, and confirm your Loan (and Book, Member) data is loaded into Power BI. Bonus: which storage mode would you pick for a 2-billion-row always-live database? (DirectQuery.)
Day 18

Build visuals & reports

~120 minutes · Learn path: Build Power BI visuals and reports

Concept — the report canvas and its three panes

A report is built on a canvas with three panes on the right: Data (your tables and fields), Visualizations (chart types and where to drop fields), and Filters. You add a visual, then drag fields onto it; Power BI groups and totals automatically.

Concept — the visuals you'll use most
  • Card — one big number (e.g. Total Loans). KPI — a number vs a target.
  • Bar / column chart — compare categories.
  • Line chart — a trend over time.
  • Table / matrix — detail rows; a matrix groups rows and columns (a pivot table).
  • Slicer — an on-screen filter people click (e.g. pick a Membership).
  • Map, pie/donut, treemap, gauge — use thoughtfully; bars and lines are usually clearest.
Concept — three levels of filter, and interactions

Filters apply at three scopes: visual (this chart only), page (every visual on the page), and report (every page). Separately, cross-filtering means clicking part of one visual filters the others — you can even change how visuals interact (Format → Edit interactions). Drill-down lets you click into a hierarchy (Year → Quarter → Month), and drill-through jumps to a detail page for the thing you clicked.

Do this — build two report pages with 9 specific visuals
  • Open your dataset → Create report. Rename the first page to Loan Overview. You'll build 5 visuals here.
  • Visual 1 — Card (Total Loans): click the Card visual. Field well: Values = Loan (count of rows, or your Total Loans measure). Title: "Total Loans". Format: font size 20, white background, teal accent bar.
  • Visual 2 — Card (Open Loans): second Card. Values = Open Loans measure. Title: "Open Loans". Red accent bar so it stands out. Place the two cards side-by-side at the top.
  • Visual 3 — Clustered Column Chart (Loans by Genre): X-axis = Book[Genre]. Y-axis = Loan (count). Title: "Loans by Book Genre". Turn on Data labels. Sort by count descending: click the "..." → Sort by → count.
  • Visual 4 — Line Chart (Loans over time): X-axis = Loan[Loan date]. Y-axis = count of Loans. Title: "Loans Over Time". This shows borrowing trends. If you have a Date table, use Dates[Month] on X for a cleaner month-by-month line.
  • Visual 5 — Slicer (by Membership): Slicer visual. Field = Member[Membership]. Style: Dropdown (Format → Slicer settings → Dropdown). Click "Student" — all 4 charts filter to student loans only. Click "Clear" to reset. This is cross-filtering in action.
  • Add a page-level filter: Filters pane → Add filter (Page level). Field = Loan[Status]. Select "Open" and "Overdue" only. Now the whole page shows only active loans. Title the page filter "Active loans view".
  • Add Page 2: click + at the bottom → rename Member Analysis. Build 4 visuals here.
  • Visual 6 — Pie Chart (Members by Membership type): Legend = Member[Membership]. Values = Member (count). Turn off the pie in future — for learning this is fine. Title: "Members by Type". Note: pie charts work OK with 4-5 slices; bars are clearer at 6+.
  • Visual 7 — Table (Overdue Loans detail): Table visual. Columns: Book[Title], Member[Full name], Loan[Loan date], Loan[Due date], Loan[Late fee]. Add a filter on this visual: Loan[Status] = Overdue. This gives staff a list of overdue loans to chase.
  • Visual 8 — KPI (Returned vs target): KPI visual. Value = Returned Loans measure. Target = Total Loans measure. Trend axis = Loan date. A green arrow if returns exceed the target fraction.
  • Visual 9 — Q&A visual: add the Q&A visual. Click it → type count of loans by genre as bar chart. Power BI builds the chart from natural language. Save the report as Library Loans.
Tip — good charts, not fancy charts Reach for a bar/column to compare and a line for time. Pies are hard to read past a few slices. Clarity beats decoration — that's a genuine PL-300 theme.
Words you learned today
  • Visual / field / field well — a chart / a column you drag / the slots you drop fields into.
  • Filter (visual / page / report) — a filter at three scopes.
  • Cross-filtering / drill-down / drill-through — click-to-filter / dig into a hierarchy / jump to detail.
  • Formatting / Q&A — styling a visual / ask for a chart in plain English.
Real world — reports and visuals in enterprise Power BI

Professional Power BI report design follows patterns used in thousands of companies:

  • One page = one audience. A sales report has a "Director view" page (KPIs and totals), a "Regional Manager view" page (breakdown by region), and a "Detail" page (individual transactions). Your Loan Overview and Member Analysis pages follow this same two-audience split.
  • Cards for the numbers that matter most. Every executive dashboard starts with 3-5 KPI cards at the top — Total Loans, Open Loans, Overdue Loans — then supporting charts below. The viewer sees the headline numbers immediately, then drills into details.
  • Slicers as self-service filters. A Membership slicer lets a librarian director see "only Student loans" without knowing how to filter in Power BI. This "self-service" filtering is why Power BI reports replace Excel-based manual reporting.
Common mistakes when building visuals
  • Dragging a numeric column to "Axis" instead of "Values". If you drag Pages (a number) to the X-axis of a bar chart, Power BI plots one bar per page count. Drag numeric measures to Values (aggregation area) and categorical columns to Axis. If a chart looks wrong, check what's in each field well.
  • Using pie charts for more than 5 categories. A pie with 8 slices is unreadable. Power BI won't stop you. Use a bar chart instead — always clearer when comparing more than 5 items.
  • Not turning on data labels. A bar chart without data labels makes viewers estimate heights. Always turn on data labels (Format → Data labels → On) for charts where the exact number matters.
  • Not saving the report. Power BI Desktop auto-saves the model but not the report layout unless you explicitly save (Ctrl+S). Always save before closing Desktop.
Practice — Day 18 hands-on checks
  • Exercise 1: On the Loan Overview page, select the Loans by Genre column chart. Hold Ctrl and select the Slicer control. In the Format tab → Edit interactions. Set the Slicer → Genre chart interaction to "None" (the no-filter icon). Now clicking the pie chart does NOT filter the column chart — but clicking the slicer still filters everything. This is custom cross-filter control — a real-world requirement when some charts are summary views.
  • Exercise 2: Add a Matrix visual to the Member Analysis page. Rows = Member[Membership], Columns = Loan[Status] (or Dates[Month if you have the date table]). Values = Count of Loans. The matrix shows how many Open/Returned/Overdue loans each membership type has — a pivot table in Power BI. Expand the matrix rows using the drill-down arrows.
  • Exercise 3: Click any bar in the Loans by Genre chart. Right-click → Drill through → (if you have a Detail page) see the drill-through option. If not, add a new page called Loan Detail. Add a Table visual showing all Loan columns. Right-click the page name → Add drill-through → add Loan[Status] as a drill-through field. Now right-clicking a status value in any chart on any page offers "Drill through → Loan Detail" — showing all loans of that status on the detail page.
  • Exercise 4: Format the report theme: Format menu → Themes → Browse for themes → download the "Colorblind safe" theme from the Power BI community gallery. Apply it. Notice how all chart colours update at once. Using an accessible colour theme is a professional standard — many enterprise reports are read by people with colour vision deficiencies.
  • Exercise 5: Add a Bookmark to capture a filtered state: apply the Slicer filter to "Student" → open View → Bookmarks panel → + Add → name it "Student view". Add another bookmark with the filter cleared → name it "All members". Add a Button to each page and set its Action → Bookmark to switch between views. This is how professional reports give users pre-set views without slicers.
Mini-quiz — Day 18

Q1 A stakeholder asks for a visual showing "the trend of loans per month over the past year." Which visual type should you use?

Q2 What is the difference between a page-level filter and a visual-level filter?

Q3 A slicer is set to filter by Member[Membership]. You want clicking a bar in the Genre chart to NOT affect the slicer. How do you achieve this?

Show answers

A1 A Line chart — it shows continuous change over time with the X-axis as months. A bar chart is for comparing categories, not showing trend over time.

A2 A visual-level filter applies only to the specific visual it's set on — other visuals on the page are unaffected. A page-level filter applies to every visual on the page simultaneously. Report-level filter applies to every page.

A3 In Format → Edit interactions: select the Genre chart, then click the slicer and set its interaction icon to "None" (the no-filter circle). This disables the cross-filter from the Genre chart to the slicer — clicking a genre bar won't change the slicer selection.

Check yourself A report with a card, bar, line and slicer, styled, with a page filter, and you used Q&A. That's an interactive, presentable report.
Day 19

Prepare & model: Power Query, relationships & DAX

~140 minutes (the deepest day) · Learn paths: Data analytics + Model data

Concept — prepare data with Power Query (it returns!)

On Day 13 you cleaned a CSV with Power Query. Power BI uses the same tool in Transform data. Each thing you click becomes an Applied step you can re-order or delete — a recipe you can re-run any time the source changes.

Concept — the transforms that matter, and query folding

Common steps: promote headers, change type, filter rows, remove/rename columns, split/merge columns, group by, merge queries (join two sources), append queries (stack two tables). Advanced: query folding — where possible, Power Query pushes work back to the source as a native query (fast); certain steps break folding, after which work happens locally.

Concept — modelling: relationships, cardinality, star schema

Real reports use several linked tables (the relationships from Day 3). A relationship has a cardinality — usually one-to-many (one Book, many Loans) — and a filter direction. BI's favourite shape is the star schema: a central fact table (the numbers/events) surrounded by dimension tables (the things you slice by). Add a dedicated Date table so time features work.

Concept — DAX: measures, columns, and context

DAX (Data Analysis Expressions) is Power BI's formula language — "Excel formulas for whole tables and totals." A measure recomputes for whatever you're looking at (the filter context); a calculated column is worked out row-by-row and stored. The powerful function is CALCULATE, which changes the filter context; and time-intelligence functions (like TOTALYTD) need that Date table.

Total Loans  = COUNTROWS(Loan)
Open Loans   = CALCULATE(COUNTROWS(Loan), Loan[Returned] = false)
Fiction Loans = CALCULATE([Total Loans], Book[Genre] = "Fiction")
Loans YTD    = TOTALYTD([Total Loans], 'Dates'[Date])
Do this — clean, model, build all DAX measures, and add the Date table
  • Power Query — clean your tables: Transform data → open Member query → promote headers if needed → set column types: Full name (text), Email (text), Join date (date), Active (true/false). Check Loan query: Loan date and Due date → set to Date type. Applied steps should show 3-5 steps. Close & Apply.
  • Model view — relationships: switch to Model view (left sidebar icon). Connect: Loan[Book] → Book[BookID] (drag from the Loan column to the Book column). Cardinality: Many-to-one. Cross-filter direction: Single (Book filters Loan). Same for Loan[Member] → Member[MemberID]. You now have a star schema: Loan is the fact, Book and Member are dimensions.
  • Build all 8 DAX measures: for each, click Modeling → New measure and type the formula exactly:
    Total Loans = COUNTROWS(Loan)
    Open Loans = CALCULATE(COUNTROWS(Loan), Loan[Returned] = FALSE())
    Returned Loans = CALCULATE(COUNTROWS(Loan), Loan[Returned] = TRUE())
    Overdue Loans = CALCULATE(COUNTROWS(Loan), Loan[Status] = "Overdue")
    Avg Loan Days = AVERAGEX(Loan, DATEDIFF(Loan[Loan date], Loan[Due date], DAY))
    Late Return Rate = DIVIDE(CALCULATE(COUNTROWS(Loan), Loan[Status] = "Overdue"), COUNTROWS(Loan), 0)
    Avg Days Overdue = AVERAGEX(FILTER(Loan, Loan[Status] = "Overdue"), DATEDIFF(Loan[Due date], TODAY(), DAY))
    And after adding the Date table below: Loans YTD = TOTALYTD([Total Loans], 'Dates'[Date])
  • Date table (Desktop): Modeling → New table → type exactly: Dates = CALENDARAUTO(). Power BI scans all date columns and builds a continuous date range. Add calculated columns to Dates:
    Year = YEAR('Dates'[Date])
    Month = FORMAT('Dates'[Date], "MMMM")
    Month number = MONTH('Dates'[Date])
    Quarter = "Q" & QUARTER('Dates'[Date])
    Day of week = FORMAT('Dates'[Date], "dddd")
    Is weekend = WEEKDAY('Dates'[Date], 2) >= 6
    Then mark it as a date table: right-click Dates → Mark as date table → Date column = Date. Now relate: Dates[Date] → Loan[Loan date] (many-to-one, Dates side = one).
  • Put Total Loans, Open Loans, Overdue Loans in Cards. Add Loans YTD in a Card. Slicer on Member[Membership] → watch all measures recompute as you click different membership types. This is the filter context at work.
Careful — this day is much richer in Desktop Power Query, the model view, relationships, the star schema, and DAX are all far smoother in Power BI Desktop (free, Windows). The browser Service can do basics. When a laptop is available, redo Day 19 in Desktop — it's exactly what PL-300 tests.
Words you learned today
  • Applied steps / query folding — the recorded transform recipe / pushing work to the source.
  • Merge / append — join two sources / stack two similar tables.
  • Relationship / cardinality / star schema — a table link / how many-to-how-many / fact + dimensions shape.
  • DAX / measure / calculated column — the formula language / a filter-aware total / a per-row value.
  • CALCULATE / time intelligence — change the filter context / date-based measures (YTD, last year).
Real world — DAX and data modelling in enterprise Power BI

DAX is what separates a basic Power BI user from a Power BI analyst. Real examples of enterprise DAX:

  • A retail company has a measure Same Period Last Year Sales = CALCULATE([Total Sales], SAMEPERIODLASTYEAR(Dates[Date])) — a time-intelligence measure that compares this year's sales to last year's automatically, reacting to any date slicer the user applies.
  • A telecom company has Churn Rate = DIVIDE(CALCULATE(COUNTROWS(Customers), Customers[Status] = "Churned"), COUNTROWS(Customers), 0) — a rate measure using DIVIDE() to safely handle division by zero, and CALCULATE() to change the filter to "churned only."
  • Every enterprise Power BI model includes a Date table. Without one, TOTALYTD, SAMEPERIODLASTYEAR, and other time-intelligence functions simply don't work. CALENDARAUTO() is the fastest way to build one.

The 8 measures you built today are the foundation of every library analytics report. The same DAX patterns appear in every industry — only the table and column names change.

Common mistakes with DAX and data modelling
  • Calculated column instead of measure for totals. If you add a calculated column called "Count" = COUNTROWS(Loan), you get the same number on every row (the total row count), not a per-category count. Aggregations that must react to filters must be measures, not columns.
  • Forgetting to mark the Date table. After creating Dates = CALENDARAUTO(), you must right-click the table → Mark as date table → Date column = Date. Without this, time-intelligence functions like TOTALYTD don't recognise the table as a date table and return errors.
  • Relationship filter direction creating unexpected results. By default, relationships filter one direction (Book filters Loan, not Loan → Book). If a visual on the Book side doesn't show loan data, check the filter direction in Model view — you may need to enable bidirectional filtering, but do so carefully as it can cause circular dependencies.
  • Dividing without DIVIDE(). [Returned Loans] / [Total Loans] returns an error when Total Loans = 0 (blank dataset). Always use DIVIDE([Returned Loans], [Total Loans], 0) — the third argument is the fallback value when dividing by zero.
Practice — Day 19 hands-on checks
  • Exercise 1: After creating all 8 DAX measures, select each one in the Data pane and look at its format: open Modeling → Format → set Total Loans to "Whole number, 0 decimals", Late Return Rate to "Percentage, 1 decimal", Avg Loan Days to "Decimal number, 1 decimal". Well-formatted measures display cleanly in cards and tables without extra work on the visual.
  • Exercise 2: In Model view, verify your relationships look correct: Loan[Book] → Book (many-to-one, Book filters Loan), Loan[Member] → Member (many-to-one), Dates[Date] → Loan[Loan date] (one-to-many, Dates filters Loan). Click each relationship line and read the properties panel — confirm cardinality and filter direction. A wrong direction here is a very common cause of incorrect report numbers.
  • Exercise 3: Add two more DAX measures:
    % Returned = DIVIDE([Returned Loans], [Total Loans], 0)
    Loans Last 30 Days = CALCULATE([Total Loans], DATESINPERIOD('Dates'[Date], TODAY(), -30, DAY))
    Place both in new Cards on the Loan Overview page. The 30-day measure shows recent activity — a common KPI in operational dashboards.
  • Exercise 4: Build a What-if parameter (Desktop only): Modeling → New parameter → Numeric range. Name = Late fee per day, min = 1, max = 20, increment = 1, default = 5. Add a new measure: Projected Late Fee = [Overdue Loans] * [Late fee per day Value]. Place a Card for this measure and the parameter slicer on the page. Drag the slicer — the projected fee updates. This "what-if" analysis is a genuine Power BI feature used by financial teams.
  • Exercise 5 — DAX challenge: Write a measure called Books Never Borrowed that counts Books that have no corresponding Loan rows. Hint: use CALCULATE(COUNTROWS(Book), NOT(Book[BookID] IN VALUES(Loan[Book]))). Place it in a Card. Compare it to Total Loans to understand what fraction of your catalogue is actually being borrowed.
Mini-quiz — Day 19

Q1 What is the difference between a DAX measure and a calculated column? Give one example of each for the library data.

Q2 Why is a dedicated Date table necessary for time intelligence functions like TOTALYTD?

Q3 Write a DAX measure that counts loans where Late fee is greater than 0 (loans that have been charged a fee).

Show answers

A1 A measure recomputes dynamically based on filter context — it produces different values in different visuals and slicers. Example: Total Loans = COUNTROWS(Loan) shows 10 for all genres, 3 for Fiction when filtered by genre. A calculated column is computed row-by-row and stored statically. Example: Loan days = DATEDIFF(Loan[Loan date], Loan[Due date], DAY) — a fixed number stored on each Loan row.

A2 Time intelligence functions need a continuous, complete date sequence to navigate: "previous year", "year-to-date", "last quarter". CALENDARAUTO() generates a contiguous date range spanning all dates in all date columns. Without marking it as the Date table, DAX doesn't know which table to use for date navigation.

A3 Loans With Fee = CALCULATE(COUNTROWS(Loan), Loan[Late fee] > 0)

Check yourself You shaped data in Power Query, linked two tables, and wrote measures that react to slicers. Key idea: a measure is a total that respects context — and CALCULATE is how you bend that context.
Day 20

Share, secure & maintain — plus your capstone

~130 minutes · the finish line · Learn path: Build visuals & reports

Concept — publish, workspaces, apps, and dashboards

From Desktop you Publish a report to a workspace in the Service. You pin the best visuals onto a dashboard (a one-screen summary), and you package a workspace's content as a Power BI app for consumers. Sharing needs a licence: Pro per-user, or Premium / Fabric capacity for large audiences.

Concept — refresh, and row-level security (RLS)

Imported data goes stale, so you set a scheduled refresh (an on-premises gateway is needed for some sources). Row-Level Security (RLS) shows different rows to different people — e.g. each regional manager sees only their region — by defining a role with a DAX rule and assigning people to it. Same least-privilege idea as Dataverse security (Day 4) and DLP (Day 16). You may also see sensitivity labels and endorsement (Promoted / Certified datasets) for governance.

Do this — publish, create RLS, pin a dashboard, schedule refresh, and export the .pbix
  • Publish (Desktop): File → Publish → Publish to Power BI. Sign in if asked. Choose My workspace. Open the link → your report appears in the Service.
  • Create an RLS role (Desktop): Modeling → Manage roles → + New role. Name = LibraryStaff. Select the Member table. In the Table filter DAX expression box, type: [Email] = USERPRINCIPALNAME(). This means: when a LibraryStaff user views the report, the Member table is filtered so they only see their own row. Save. Now go back to the Service.
  • Assign users to RLS role (Service): open your dataset → Security (three dots → Security). Find LibraryStaff → + Add people. Add your own email address. Save. Now click Test as role → LibraryStaff — the report filters to only your Member row. Click "Now viewing as: LibraryStaff" → Stop viewing. This is exactly how an admin would verify RLS before deployment.

Real world — publishing, sharing, and RLS in enterprise Power BI

The sharing and security patterns you built today are standard enterprise practice:

  • A multinational bank's Power BI workspace has 200 reports shared with 3,000 employees. RLS on the Transactions dataset ensures each branch manager sees only their branch's data — one dataset, 200 branches, all secured by USERPRINCIPALNAME(). Without RLS, they'd need 200 separate datasets.
  • A retail chain schedules refresh at 2am daily from their on-premises SQL server via the on-premises data gateway. By 7am when store managers open Power BI, last night's sales are already there — no manual exports, no waiting for IT.
  • Power BI apps are used to give business users a clean, curated experience: instead of seeing the whole workspace with draft reports and test datasets, they see only the published, approved visuals in the app. The workspace is for analysts; the app is for consumers.
Common mistakes with sharing and security
  • Testing RLS without "View as role." After creating an RLS role, many beginners try to share the report and ask someone else to test it — a slow feedback loop. Use the built-in "Test as role → LibraryStaff" button in the Service to see exactly what a role member would see, in seconds.
  • Sharing from Desktop instead of the Service. You cannot share a Power BI report directly from Desktop — you must first publish to the Service, then share from there. Desktop is for authoring; Service is for sharing.
  • Scheduled refresh without checking the gateway. Refresh works automatically for cloud sources (Dataverse, SharePoint). For on-premises sources (SQL Server, local Excel), you need an on-premises gateway installed on a machine that runs 24/7. Always check the data source type before setting up refresh.

Mini-quiz — Day 20

Q1 What is Row-Level Security, and at what layer does it apply (visual, dataset, or workspace)?

Q2 You set up a scheduled refresh for a Power BI dataset connected to a local Excel file on your PC. The refresh fails every night. Why?

Q3 What is the difference between sharing a report and publishing a Power BI app?

Show answers

A1 Row-Level Security is a filter applied at the dataset level that restricts which rows a user can see based on their identity (USERPRINCIPALNAME()). It applies at the dataset layer — not the visual — so it cannot be bypassed by changing visuals or filters in the report.

A2 The Excel file is on a local PC that is not running or accessible at the time of refresh. Cloud-based refresh can't reach local files — you need the on-premises data gateway installed on that PC to bridge the connection. Alternatively, move the file to OneDrive or SharePoint (cloud) and refresh works without a gateway.

A3 Sharing a report gives specific people access to that report via a link — they see the report in their workspace. Publishing a Power BI app creates a curated, navigation-friendly package (app) that can include multiple reports and dashboards — consumers open the app URL and see only what you've chosen to include, not the raw workspace. Apps are better for large audiences; sharing is better for one-to-one collaboration.
